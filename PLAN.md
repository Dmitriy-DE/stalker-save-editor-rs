# План: редактор сохранений на Rust

Состояние на 2026-10-10. Эталон — выпущенный C#-редактор 1.3.1
(`Dmitriy-DE/S.T.A.L.K.E.R.-Save-Editor`, тег `v1.3.1`).

## Зачем

C#-версия упёрлась в потолок среды, а не кода: 109 МБ в простое при 9 МБ собственных объектов, пакеты 59–88 МБ,
холодный старт около 1,5 с. Гибрида не будет: всё на Rust.

## Два главных правила

**1. Не копия, а лучше.** Эталон задаёт пол, а не потолок. Совпадать с C# обязано только то, чему судья — игра:
что прочитано из сейва и какие байты записаны. Всё остальное — устройство, скорость, память, интерфейс, набор
проверок — делается заново и лучше. Перенос «один в один» не принимается: в каждом пакете написано, что именно
должно стать лучше и как это измеряется. Где эталон ошибается, ошибку не копируем: расхождение записывается в
таблицу «Расхождения с эталоном» ниже с доказательством.

**2. Всё своё.** Чужих библиотек нет: ни крейтов, ни C++. Разрешено только `std` и вызовы самой операционной
системы. Причина та же, по которой фиксы живут внутри редактора: чужой код — это чужие размеры, чужие ошибки и
чужие обновления.

| Что | Чем было | Чем становится |
|---|---|---|
| Kraken (сейвы S2) | C++ `ooz` через FFI | свой декодер и кодировщик на безопасном Rust |
| LZO1X, LZHUF, CRC32, SHA-256 | свой C# | свой Rust в `sse-codecs` |
| JSON, VDF, LTX, XML, кодовые страницы | `System.Text.Json` и свой код | свои читалки; данные редактора запекаются при сборке в двоичные таблицы, на старте ничего не разбирается |
| Картинки | PNG через Skia, DDS свой | свой DDS; значки запекаются при сборке в один атлас своего формата; PNG-декодер нужен только сборке |
| Звук | NVorbis, 8,8 МБ звуков в пакете | свой декодер Vorbis: звуки берутся прямо из архивов установленной игры, в пакете их нет; вывод через API системы |
| Подпись обновлений | `ECDsa` из .NET | своя проверка ECDSA P-256 (только проверка, секретов нет) |
| HTTPS | `HttpClient` | сетевой стек системы (WinHTTP, `libcurl` системы на Linux и macOS). **TLS сами не пишем** — это единственное место, где своё было бы хуже |
| Steam | `libsteam_api` через P/Invoke | та же библиотека Steam, объявления вызовов написаны руками |
| Интерфейс | Avalonia + Skia | своя библиотека `sse-ui`: окно через API системы, свой растеризатор, свои шрифты (замер U0 ниже) |
| Python-инструменты (проверки фиксов, генераторы фикстур) | 60 скриптов | Rust: проверки скриптов игры становятся крейтом `sse-lint` и работают не только в CI, но и в редакторе как «проверка модов»; генераторы фикстур становятся построителями в тестах |
| Тестовая обвязка Lua (`lua_harness`) | стоковый Lua 5.1 | остаётся инструментом разработчика на стоковом Lua, в пакет не входит. Свой интерпретатор Lua — отдельное решение позже (он дал бы проверку скриптов модов прямо в редакторе) |

Весь `unsafe` и все объявления вызовов системы живут в одном крейте `sse-sys` (файлы с позиционным чтением, окно,
звук, сеть, Steam, счётчик выделений памяти для тестов). В остальных крейтах `unsafe` запрещён линтом.

Не переписывается только то, что исполняется не у нас: мод-компаньон на Lua (работает внутри игр) и сами данные
(каталог фиксов, каталоги имён, переводы, сигнатуры вылетов, значки, шрифты, звуки, фикстуры). Формат манифеста
обновлений и ключ подписи остаются, чтобы 1.3.x обновился в 2.0 своим же обновлением. Веб-издание — тот же код,
собранный под WASM.

## Что именно станет лучше, чем в C#

| Где | C# 1.3.1 | Rust 2.0 | Как проверяется |
|---|---|---|---|
| Образ сейва | 6–10 копий при правке | исходный + рабочий + один на проверку | счётчик выделений в тесте |
| Модель сейва | граф объектов | буфер + индекс смещений | память на сейв в библиотеке |
| Правка | по этапу на вид правки, каждый раз полный разбор | набор изменений за один проход | время правки, байты вне диапазонов не тронуты |
| Отмена | снимки образов | наборы изменений (байты, не образы) | 100 шагов ≤ 1 МБ |
| Библиотека сейвов | полный разбор каждого сейва | индекс на диске в своём формате, список виден сразу, разбор в фоне пулом потоков | 333 сейва: список ≤ 100 мс при тёплом индексе |
| Данные редактора | JSON разбирается на старте | двоичные таблицы, запечённые при сборке | 0 разборов на старте |
| Значки | 7 МБ PNG, кэш Skia | один атлас своего формата, читается кусками | вес пакета, память |
| Архивы игр | чтение в память | позиционное чтение, только запрошенное | архив 1 ГиБ ≤ 20 МиБ |
| Интерфейс | перерисовка кадрами | перерисовка только изменившегося, 0% процессора в простое, списки только виртуальные | замер простоя, 2000 строк без рывков |
| Поток интерфейса | замирания до 0,4 с | ≤ 50 мс: вся работа сообщениями рабочим потокам | замер в CI |
| Проверки | Save Doctor, CLI и запись проверяют по-разному | один движок правил | одни и те же ответы в трёх местах |
| Проверка скриптов игры | Python, только у разработчика | `sse-lint` в редакторе: проверка установленных модов | тесты на шести установках |
| Kraken | C++, `unsafe`, отдельная сборка | безопасный Rust, собирается под WASM | векторы, фаззинг, сейвы владельца |
| Фаззинг | отдельный прогон вручную | детерминированные мутации в `cargo test` для каждой читалки | CI |

## U0: выбор библиотеки интерфейса (замер 2026-10-03)

Один экран в трёх вариантах: список сейвов, таблица на 2000 строк, панель предмета, тёмная тема, русский и
китайский текст. Linux, окно 1260×760, сборка с `lto`, без отладочных данных.

| | Память в простое | Размер программы | Первый кадр | Чужой код |
|---|---:|---:|---:|---|
| C# 1.3.1 (весь редактор) | 109 МБ | 59 МБ пакет | ~1,5 с | Avalonia, Skia, .NET |
| egui (OpenGL) | 94 МБ | 5,2 МБ | 0,10–0,14 с | ~250 крейтов |
| Slint (OpenGL) | 107 МБ | 13,6 МБ | ~0,16 с | ~400 крейтов, fontconfig |
| Slint (программный рендер) | 33 МБ | 13,6 МБ | ~0,16 с | то же |
| **Своя (только `std`)** | **10 МБ** (21 МБ при масштабе 200%) | **0,37 МБ** | **0,03–0,15 с** | нет |

Своя: протокол X11 напрямую через сокет, свой растеризатор с покрытием, свой разбор TrueType; кириллица и
иероглифы рисуются. Полная перерисовка окна 6–7 мс (при 200% — 24–29 мс, поэтому перерисовка только изменившегося
и общая память с сервером обязательны).

**Выбор: своя библиотека `sse-ui`.** Цена, которую платим сознательно: виджеты, раскладку, ввод текста, буфер обмена
и четыре способа открыть окно (X11, Wayland, Windows, macOS) плюс холст в браузере пишем сами. Чего в первой
версии не будет: ввода иероглифов через системный метод ввода (в редакторе печатают числа и поиск латиницей или
кириллицей) и поддержки экранных дикторов. Замерено только на Linux; Windows и macOS проверяются сборками CI и
владельцем.

| Что | Эталон | У нас | Доказательство |

## Архитектура

```
sse-app      окно: только рисует и принимает ввод; всё остальное — сообщения рабочим потокам
sse-cli      командная строка = поверхность сравнения с эталоном
─────────────────────────────────────────────────────────────────────────
sse-doctor   проверки, вылеты      sse-fixes     каталог фиксов     sse-lint   проверки скриптов игры
sse-companion мод-компаньон        sse-steam     облако, достижения sse-update обновление
sse-xray     сейвы ТЧ/ЧН/ЗП и EE   sse-s2        сейвы S.T.A.L.K.E.R. 2
sse-content  файлы установленной игры            sse-catalog имена, каталоги, переводы
sse-storage  запись на диск, бэкапы, черновики, поиск сейвов
sse-codecs   LZO1X, LZHUF, CRC32, SHA-256, Kraken, JSON, VDF, P-256, inflate
sse-core     ошибки, SaveBuffer, Cursor, набор правок, возможности
sse-sys      единственный unsafe: вызовы системы
```

Крейты форматов, кодеков и содержимого не знают о файловой системе и потоках: принимают байты, отдают результат.

## Совместная работа

В репозитории нет постоянного закрепления кода за агентами или файлами. Задача может требовать изменений в нескольких
крейтах, `sse-ui`, CI и `tools/`; временная маршрутизация задач в `TASKS.md` не запрещает такие изменения. На каждую
задачу открывается один PR из ветки от свежего `origin/main`; собственные PR не вливаются. Владелец проверяет и
интегрирует изменения, а ключи подписи и выпуск остаются у владельца.

Живые проверки игры и Steam разрешены в пределах пользовательского разрешения. Перед ними сохраняются копии всех
затрагиваемых файлов или состояния, после них исходное состояние восстанавливается. Результаты делятся на проверку
кодом/тестами и реальный запуск; синтетические round-trip-тесты не подтверждают загрузку сейва игрой.
